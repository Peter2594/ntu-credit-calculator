# 大學生學分計算表 — 設計文件

日期：2026-09-16
狀態：設計已確認，待撰寫實作計畫

## 背景

起點是一份為單一學生手工維護的「學分存摺」artifact：貼上歷年成績與選課結果，人工判定每門課的學分歸屬，算出距離畢業還差多少。那份東西證明了需求是真的，但每次改課都要重算一遍，而且只服務一個人。

這個專案把那套流程變成工具。

## 目標與使用者

給**全台大學生**用的學分進度工具。使用者貼上 myNTU 歷年成績，工具算出各分類進度與缺口，並能試算「再修這幾門會怎樣」。

三個核心功能：

1. **盤點** — 已修課程的分類與進度
2. **試算** — 加入假設課程，即時看缺口變化
3. **課表** — 手動輸入本學期／未來學期課程，節次格線與衝堂檢查

## 架構決策

### 純靜態，部署到 GitHub Pages

沒有後端、沒有資料庫。使用者資料只存在自己瀏覽器的 localStorage，不經過任何伺服器 —— 對「貼成績單」這種資料而言這是正確的選擇，介面上要明講。

### 技術選型：Vite + React + TypeScript

不用 Next.js：static export 要額外處理 `basePath`、image loader、路由，而這是純單頁工具、無 SSR 需求，Next 的能力用不到卻要繞設定。

不用純 HTML/JS：狀態夠複雜（多學程、已修／計畫課程、手動覆寫、多學期切換），React 的元件化較好維護。

### 畢業門檻由使用者填寫，不自動帶入

**決策：進站時讓使用者填六個數字，不爬資料、不傳 PDF。**

考慮過並否決的兩條路：

**預先爬取各系規定。** `curri.aca.ntu.edu.tw/NTUVoxCourse/index.php/uquery/tc?DPRNDPT={系所代碼}&QPYEAR={學年度}` 確實回傳結構化的應修學分表，`/uquery/cou`（加 `MSLGRD=1~4`）回傳系訂必修科目表。資管系（7050）已實測可用。但這會讓專案背上「每年為每個系維護資料」的責任，而且只驗證過一個系，其他系是否同格式未知。

**讓使用者上傳系上的 PDF。** 否決，理由是實測過的技術障礙：台大的課程規定 PDF 字型缺 ToUnicode 對照表，文字層抽出來是亂碼（實測學校的課程手冊 PDF，pypdf 抽取失敗，最終靠視覺辨識才取得內容）。瀏覽器的 pdf.js 會遇到同樣問題且無視覺模型可救。即使抽得出文字，各系 PDF 排版互異，等於每系一套 parser。

**手填的優點**：零解析、零維護、所有系所通吃、甚至可用於其他學校。成本是使用者一分鐘的輸入。

未來可選的加分項：把已驗證的系所做成預設值，使用者選系後自動填入、仍可修改。**這是增強，不是前提。**

### core／ui 分離

介面將委由 Google AI Studio 產生，因此邏輯與畫面必須徹底切開：

```
src/core/          純 TypeScript，零 React 相依
  types.ts           型別定義
  parser.ts          成績單解析
  engine.ts          歸類、統計、溢出規則
  storage.ts         localStorage 讀寫
src/ui/            AI Studio 產出的介面，只呼叫 core
```

AI Studio 重做幾次介面都不會動到算分邏輯，且 core 可獨立測試。

## 資料模型

```ts
type Category =
  | '系訂必修' | '限本系選修' | '一般選修'
  | '國文' | '外文' | '通識' | '體育' | '不計入'

type Requirements = {
  total?: number             // 畢業總學分，如 134
  major?: number             // 系訂必修，如 58
  common?: number            // 共同必修＋通識，如 24
  elective?: number          // 選修合計，如 52
  electiveInMajor?: number   // 其中限本系，如 21
  pe?: number                // 體育，不計入 total
}
// 主修填滿；輔系通常只有 total

type Program = {
  id: string
  kind: '主修' | '雙主修' | '輔系'
  name: string               // "資訊管理學系"
  deptPrefix: string         // "705"
  requirements: Requirements
}

type Slot = {
  day: 1 | 2 | 3 | 4 | 5
  periods: string[]          // ["7","8","9"] | ["A","B","C","D"]
  room?: string
}

type Course = {
  id: string
  name: string
  code?: string              // 課號，如 IM3008
  identifier?: string        // 課程識別碼，如 "705 31300"
  credits: number
  grade?: string             // A+ / A / 通過 / 停修；undefined 表示計畫中
  semester: string           // "113-1" / "115-1" / "暑修"
  genEdDomain?: string       // 通識領域，如 "A6" / "A58"
  assignments: { programId: string; category: Category }[]
  overridden: boolean        // 使用者是否手動改過分類
  slots?: Slot[]
}
```

`assignments` 是**陣列而非單值**，因為同一門課真的會被算兩次。台大規定明文：

> 本系學生修讀他系之雙主修必修科目及指定選修學分，計入選修學分

一門雙主修的必修課同時計入雙主修進度與本系選修學分。單值型別表達不了這件事，事後補會很痛。

## 歸類引擎

### 自動判定規則

按順序套用，第一個命中者勝：

| 判斷依據 | 歸類 |
|---|---|
| 成績 = 停修 | 不計入 |
| 有通識領域欄（A1–A8） | 通識 |
| 識別碼前三碼 = `101` 或課號 `CHIN*` | 國文 |
| 識別碼前三碼 = `102` 或課號 `FL*` | 外文 |
| 識別碼前三碼 = `002` 或課號 `PE*` | 體育 |
| 識別碼前三碼 = 該 program 的 `deptPrefix` | **本系課，需人工確認必修或選修** |
| 其他 | 一般選修 |

**「前三碼」的定義**：取識別碼字串的前三個字元，不做其他處理。識別碼格式不一致——`705 31300`（有空格）、`705E22200`（無空格）、`700E10401`、`201 49810` 都出現過——但前三碼一律是開課單位代碼，直接 `slice(0, 3)` 即可。

### 唯一需要人介入的一格

`705 31300 資料庫管理`（系訂必修）與 `725 U3350 軟體專案管理`（系訂選修）從識別碼看都是本系課，但歸類不同，而成績單沒有必選修欄位可以分辨。

處理方式：**貼上後一次性確認**。工具列出所有課、預設分類已填好，使用者掃一遍只勾出本系必修那幾門，結果存入 localStorage，之後相同課號自動沿用。

### 抵免與覆寫

自動比對無法處理系辦裁量的抵免。實際案例：

- `ECON1020 個體經濟學原理與實習`（4 學分）抵 `ECON1022 個體經濟學原理`（3 學分），餘 1 學分計入一般選修
- 課名不同、但經系辦核可替代必修的課程

因此**每門課的分類都必須可手動覆寫**，覆寫後標記 `overridden: true`，重新解析時不被自動規則蓋掉。

### 上限與溢出規則

這些規則來自台大必修課程查詢系統的備註欄，是總數能否對得上的關鍵：

1. **超修之通識**（A1–A8 無 `*` 者）不計入選修學分
2. **超修之大學國文**不計入選修學分
3. **超修之外（英）文領域學分計入選修學分**（與前兩條相反，別寫錯）
4. **系訂必修因抵免而溢出**的學分計入一般選修
5. **體育學分不計入**畢業應修總學分
6. **服務學習**自 114 學年度起不計入畢業總學分；115 學年度起入學者可計入選修，至多 2 學分
7. 各分類超出門檻的部分不再累加進畢業總數，但實修學分仍應顯示

引擎要同時輸出「實修學分」與「計入畢業學分」兩個數字，兩者會因上述規則而不同。

## 畫面

給 AI Studio 的五個畫面：

1. **學程設定** — 新增主修／雙主修／輔系，每個填門檻數字與識別碼前綴
2. **匯入** — 貼成績單 → 解析預覽 → 一次性分類確認
3. **儀表板** — 每個學程一組進度條與缺口
4. **課表** — 手動新增課程（課名／節次／教室／學分／識別碼）、節次格線、衝堂提示
5. **試算** — 加入假設課程，即時看進度變化

節次時間依台大作息：第 1 節 08:10、第 2 節 09:10、第 3 節 10:20、第 4 節 11:20、第 5 節 12:20、第 6 節 13:20、第 7 節 14:20、第 8 節 15:30、第 9 節 16:30、第 10 節 17:30、A 節 18:25、B 節 19:20、C 節 20:25、D 節 21:20。

## 測試策略

core 的每個模組獨立測試。

### 測試資料一律匿名化（硬性要求）

這個 repo 會公開到 GitHub Pages，**任何 commit 進版本庫的測試資料都必須是合成的**。

設計時參考過真實成績單，它涵蓋了抵免、溢出、停修、通過不計分、跨系多學期等幾乎所有邊界情況，是理想的迴歸基準。但成績本身是敏感資料，**不得進入版本庫**。

作法：

1. **合成 fixture**：保留那份資料的「結構」——同樣的邊界情況組合——但課程名稱、識別碼、成績全部重新編造。目標是讓每一條上限與溢出規則都至少被一個案例命中。
2. **真實資料留在本機**：若開發過程要拿真實成績單對答案，檔案放在 `fixtures/local/`，並列入 `.gitignore`。
3. **commit 前實際檢查**，不靠印象：

   ```bash
   git grep -nE "(A\+|停修|[0-9]{9})" -- fixtures/ | grep -v fixtures/local
   ```

   以及 `git log -p` 掃過歷史，確認沒有任何一次 commit 夾帶過真實成績。一旦進了歷史，改 `.gitignore` 是救不回來的。

### 合成 fixture 必須覆蓋的案例

| 案例 | 為什麼重要 |
|---|---|
| 高學分課抵低學分必修，餘數溢出到一般選修 | 最容易算錯的一條 |
| 課名不同但經核可的替代 | 驗證手動覆寫不被自動規則蓋掉 |
| 通識超修 | 超出部分不計入選修 |
| 外文超修 | 與通識相反，**要**計入選修 |
| 停修 | 完全不計入 |
| 通過／不計分 | 計學分但不計 GPA |
| 體育 | 不計入畢業總數 |
| 雙主修課程雙重計算 | `assignments` 陣列的存在理由 |

## 實作順序

分兩階段，各自一份實作計畫：

**Phase 1 — core**：型別、成績單 parser、歸類引擎、上限與溢出規則、localStorage。全部用測試驅動，以上述真實資料當 fixture。這階段結束時，邏輯已經完全正確，只是沒有畫面。

**Phase 2 — ui**：學程設定、匯入、儀表板、課表、試算五個畫面，接上 core。介面由 AI Studio 產出後整合。

先做 core 的理由是它可以獨立驗證對錯；介面則會反覆重做，不該讓邏輯跟著動。

## 非目標

明確不做：

- 不自動爬取或帶入各系畢業規定（未來可加）
- 不解析 PDF
- 不解析選課結果（課表改為手動輸入）
- 不做帳號系統，資料只在 localStorage
- 不處理跨校、不處理研究所
- **不做 GPA 計算**。使用者選定的範圍是盤點／試算／課表三項，GPA 不在其中。（成績資料其實已經在手上，之後要加成本很低——雙制換算規則見下方附錄——但不列入本版。）
